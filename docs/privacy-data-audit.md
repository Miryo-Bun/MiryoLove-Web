# MiryoLove Web: техническая инвентаризация обработки данных

**Дата проверки:** 7 ноября 2026 года  
**Назначение:** фактические технические сведения для последующей оценки специалистом по праву.  
**Статус:** технический аудит, не юридическое заключение; соответствие Федеральному закону № 152-ФЗ не устанавливается.

## 1. Краткое резюме

Изучены исходный статический сайт, его подготовленная публичная копия, активная конфигурация Caddy, доступная часть конфигурации systemd-journald, метаданные журналов, файловые права, служебные таймеры, DNS-ответ NS и доступные сведения о Snapper.

В HTML/CSS/JavaScript подготовленной копии не обнаружены формы отправки, запросы приложения к API, аналитика, рекламные пиксели, встроенные внешние страницы, внешние шрифты или чтение/запись HTTP-cookie. JavaScript сохраняет выбранный язык в `localStorage` и факт закрытия информационного уведомления в `sessionStorage`. В проверенном коде эти значения не отправляются на сервер.

При этом отсутствие access log для главного сайта **не означает**, что никто не получает сетевые сведения о посещении. Caddy принимает соединение и запрос; оператор сети, DNS-резолвер, хостинг-провайдер и другие инфраструктурные участники могут получать технические метаданные. Их фактический состав, хранение и получатели из локальной конфигурации не установлены.

В активном Caddyfile access-log-директива `log` для главного сайта отсутствует. Caddy направляет стандартный вывод в systemd journal. В сохранённой выборке журнала обнаружены структурированные request-объекты в сообщениях Caddy об ошибках обратного прокси для хостов, не относящихся к `miryolove.org`: поля включали IP клиента, User-Agent, URI, метод, заголовки и TLS-сведения. Значения этих полей в отчёт не копировались. Это подтверждает, что общий журнал хоста способен содержать такие данные, но не подтверждает наличие этих запросов в журнале главного сайта.

Финальная read-only проверка 7 ноября 2026 года подтвердила через Caddy admin API и `/etc/caddy/Caddyfile`, что загруженный runtime и файл указывают на `/mnt/Manchild/Project/MiryoLove/MiryoLove Web-deploy`. Это исправляет более раннее наблюдение root `/mnt/Manchild/Project/MiryoLove/Web/1`; способ и точное время изменения/reload не установлены. См. раздел 18 для свежих результатов и ограничений.

## 2. Область аудита

В область включены только:

- исходный каталог `MiryoLove Web`;
- подготовленная публичная копия `MiryoLove Web-deploy`;
- Caddy, непосредственно обслуживающий `miryolove.org` и `www.miryolove.org`;
- системные журналы и настройки, доступные текущему пользователю без повышения привилегий;
- сведения о DNS, TLS и заданиях резервного копирования/снимков, доступные локальной проверке.

Текущий доступный Caddyfile и runtime содержат только `miryolove.org` и `www.miryolove.org`; дополнительных active site blocks и imports не обнаружено. Сохранённый старый кандидат содержит другие hostname, а journald — исторические записи других hosts; это не подтверждает, что они входят в текущий runtime.

Предположение о несовершеннолетии владельца предоставлено заказчиком и не проверялось. В отчёте нет юридических выводов о дееспособности или полномочиях лица.

## 3. Методология и ограничения

Проверки выполнялись в режиме чтения:

- чтение HTML/CSS/JavaScript и поиск API, storage, форм, cookie API, iframe, аналитики и внешних ресурсов;
- инвентаризация публичного deployment-каталога и сравнение копий с исходниками;
- `systemctl show`, `systemctl cat`, `ps`, `ss`, `namei`, `stat`, `getfacl`, `findmnt`;
- чтение `/etc/caddy/Caddyfile`, проверка импортов и каталога `/etc/caddy/conf.d`;
- `journalctl -u caddy -o json` с агрегированием только типов событий и имён полей; значения запросов, адреса, заголовки и содержимое пользовательских запросов не выводились в отчёт;
- `systemd-analyze cat-config systemd/journald.conf`, `journalctl --disk-usage`, `journalctl --list-boots`;
- перечень systemd timers и проверка доступных метаданных Snapper;
- DNS-запрос NS для домена;
- проверка страниц подготовленной копии в локальном браузере, без сканирования внешних систем.

Не использовались `sudo`, сетевое сканирование, нагрузочные тесты, запросы к базам данных или просмотр содержимого резервных копий. Для некоторых данных Snapper прав чтения не было; это зафиксировано ниже. Провайдерские панели, договоры, сетевые журналы вне хоста и аппаратная инфраструктура недоступны.

## 4. Архитектура сайта и фактический deployment

### Подготовленная копия

`MiryoLove Web-deploy` содержит 17 публичных файлов: 10 HTML-файлов (девять страниц и пользовательская 404), `styles.css`, `script.js`, три используемых изображения, `robots.txt` и `sitemap.xml`. В копии нет `.git`, `docs/`, служебных отчётов, конфигураций разработки, README, LICENSE, симлинков или файлов, похожих по именам на секреты и базы данных. Локальные HTML-ссылки и пути к ресурсам сопоставлены; после удаления публичной дорожной карты копия повторно синхронизирована и проверена на совпадение файлов сайта с исходниками.

В CSS используется системный стек шрифтов; файлов шрифтов и внешних font URL нет. Статические HTML-страницы используют локальные CSS, JavaScript и изображения. В браузере не было обнаружено автоматических запросов к внешним доменам при просмотре страниц. Внешние ссылки являются обычными навигационными ссылками и обращаются к адресату при переходе пользователя.

### Активный Caddy root

Согласно `/etc/systemd/system/caddy.service` (получено через `systemctl cat caddy`), активная служба запускается с `--config /etc/caddy/Caddyfile`. В site block главного домена указан root:

`/mnt/Manchild/Project/MiryoLove/MiryoLove Web-deploy`

Текущий активный Caddy runtime обслуживает подготовленную публичную копию. Исходный проект находится отдельно в `MiryoLove Web`; обе копии проверены и основные публичные `index.html`/`script.js` до локальных изменений совпадали. Внешние read-only HTTP проверки также подтвердили главные страницы и статические ресурсы.

`localStorage` и `sessionStorage` — отдельные API браузера, не HTTP-cookie. Они доступны JavaScript того же origin. В проверенном JavaScript нет `fetch`, `XMLHttpRequest`, `sendBeacon`, WebSocket или кода, который включает эти значения в запросы.

Не обнаружены формы регистрации, обратной связи, подписки или отправки сообщений, встроенный чат, API-запросы сайта, сторонние библиотеки, iframe, аналитика, рекламные пиксели или автоматические внешние шрифты. Обычные внешние ссылки присутствуют, но не загружают адресаты автоматически.

В опубликованных политиках прямо указано, что официальный контакт по вопросам приватности пока не опубликован и сведения о провайдере/логах нужно уточнить.

## 6. Данные, которые может получать Caddy

Активный Caddy block для главного сайта содержит `root`, `encode`, security headers и `file_server`; отдельной директивы `log` нет. Успешные запросы к статическим файлам не имеют включённого в этом site block access log.

При установлении HTTP/TLS-соединения сервер технически получает данные, необходимые для ответа, например IP источника соединения, запрошенный host/path, метод и сетевые/TLS-параметры. Сам факт приёма соединения не доказывает, что каждое поле сохраняется в журнале. Логи провайдера, внешнего proxy/CDN или сетевого оборудования не доступны.

Текущий активный Caddyfile и runtime JSON содержат только `miryolove.org`/`www.miryolove.org`; reverse proxy не загружены. При этом Caddy service и systemd journal могут содержать исторические события других host из предыдущей конфигурации или иных runtime состояний; текущая конфигурация не доказывает изоляцию ранее сохранённых записей.

Локальный административный API Caddy слушает `127.0.0.1:2019` (`ss -ltnp`); не наблюдался listener этого API на внешнем интерфейсе. Публичные listeners хоста — 80 и 443. Внешние сетевые ACL/firewall в рамках этой проверки не исследовались.

## 7. Системные журналы и фактическое наблюдение Caddy

### Настройка

- `caddy.service` задаёт `StandardOutput=journal`; `StandardError=inherit`. Отдельного активного journald drop-in не найдено.
- В `/etc/caddy/Caddyfile` нет access-log директивы; imports отсутствуют. Read-only admin API подтвердил отсутствие configured access logging.
- `/var/log/caddy` имеет mode `750`, владелец `caddy:caddy`; текущему пользователю отказано в доступе к его списку. Поэтому наличие/размер файлов в каталоге не установлены.
- Caddy runtime сообщения, в том числе TLS/ACME и ошибки, доступны через systemd journal.
- В `/etc/logrotate.d` не найдено правила для Caddy или journald.

### Системный журнал

`/var/log/journal` существует, поэтому journald хранит persistent journal. В `/etc/systemd/journald.conf` и доступных drop-ins значения `Storage`, `SystemMaxUse`, `SystemKeepFree`, `MaxRetentionSec`, `MaxFileSec` и другие проверенные лимиты явно не заданы; используются значения systemd по умолчанию. Конкретный срок хранения из конфигурации не установлен. `MaxFileSec` в файле оставлен закомментированным, поэтому комментарий не является активной настройкой.

По `journalctl --disk-usage` архивные и активные журналы всех служб занимали 1.2 GB на момент проверки. Это общий объём systemd journal, **не** объём Caddy. В доступной выборке за последние семь дней было 4,323 Caddy journal entries; это окно выборки, а не retention policy.

### Поля запросов в сохранённых сообщениях

В агрегированной выборке за последние семь дней было 110 структурированных request-объектов в сообщениях `http.log.error` (109) и `http.handlers.reverse_proxy` (1). Все были отнесены к host, отличным от `miryolove.org`/`www.miryolove.org`. В объекте есть поля `client_ip`, `remote_ip`, `remote_port`, `host`, `method`, `proto`, `uri`, `headers`, `tls`. В 85 из 110 request headers присутствовал Referer, в 34 — Cookie, во всех — User-Agent. Значение Authorization в выборке не наблюдалось; сериализация полного headers object означает, что возможные заголовки могут попадать в диагностическую запись. Никакие значения IP, заголовков, URL или query не выводились.

В этой же выборке request-объектов главного домена не найдено. Это не доказывает, что сайт никогда не журналировался: выборка ограничена сохранёнными Caddy messages; активная и исторические конфигурации могли различаться, а внешние слои не проверены.

Caddy journal также содержит системные TLS/ACME-события. В его сообщениях обнаружены обращения к ACME endpoints Let’s Encrypt production и staging. Часть записей содержит попытки challenge и ошибки; по историческому журналу нельзя делать вывод о текущем состоянии сертификата или о результативности каждого challenge. ACME-процесс раскрывает CA как минимум доменное имя для выпуска/проверки сертификата; конкретные данные, переданные провайдеру при каждом обращении, в этом отчёте не перечисляются.

### Доступ

Журналы находятся под `/var/log/journal`, каталог принадлежит `root:systemd-journal`; файлы имеют режим `0640`. На каталоге есть ACL для групп `wheel` и `adm`. Пользователь `miryo_bun` входит в `wheel` и в текущем окружении смог прочитать агрегированную выборку через `journalctl`. Содержимое журналов может включать IP и URL; доступ к журналам является чувствительным административным доступом.

## 9. Резервное копирование и хранение

- Найдены включённые `snapper-timeline.timer` и `snapper-cleanup.timer`; `snapper-backup.timer` отключён. `snapper list-configs` показывал конфигурацию `root` для `/`.
- Чтение параметров и списка снимков командой Snapper завершилось сообщением «Нет прав». `sudo` не использовался. Поэтому нельзя подтвердить частоту/retention снимков, список исключений, содержимое, доступ, наличие копирования на другой носитель или фактический срок хранения.
- Путь сайта `/mnt/Manchild` расположен на отдельном ext4 filesystem. `/var/log` расположен на отдельном btrfs mount. Snapper-конфигурация `root` сама по себе не доказывает, что содержимое этих отдельных mount включено в снимки.
- В активной конфигурации службы не выявлены явные задания архивирования сайта. Это не доказывает отсутствия внешнего, гипервизорного или провайдерского backup.
- Содержимое snapshot/backup не открывалось и не копировалось.

## 10. Контроль доступа и технические риски

- Caddy запускается как `caddy:caddy`; `/var/lib/caddy` имеет права `0750` и предназначен для состояния TLS/сертификатов Caddy. Файлы внутри хранилища не открывались.
- `/var/log/caddy` имеет права `0750`; содержимое недоступно текущему пользователю. Persistent journal доступен для чтения; точный состав прочих лиц и служб с доступом отдельно не инвентаризировался. В Caddy errors других hosts есть IP/URI/headers.
- Caddy admin API наблюдался на loopback `127.0.0.1:2019`. Это не заменяет проверку firewall или полной сетевой конфигурации.
- Runtime и текущий on-disk root указывают на deployment-копию. История изменения/reload не установлена; предыдущее наблюдение старого root устарело.
- Лимиты и сроки хранения journal явно не закреплены конфигурацией. Есть потенциальное хранение технических данных до автоматической ротации/освобождения места, но точный срок неизвестен.
- Текущий runtime не имеет других site blocks, но сохранённый journal содержит исторические записи других hosts; агрегированное хранилище не изолировано по доменам/времени.
- Не подтверждены access controls провайдера, сетевые журналы, back-ups, мониторинг, обработчики TLS вне локальной машины, процедура удаления и реагирования на запросы.

## 12. Подтверждённые факты

1. `/etc/systemd/system/caddy.service` загружает `/etc/caddy/Caddyfile`; активный service process работает как `caddy:caddy`.
2. Главный site block/runtime обслуживает `miryolove.org` и `www.miryolove.org` из `/mnt/Manchild/Project/MiryoLove/MiryoLove Web-deploy`, с `file_server`, compression и security headers.
3. Активный runtime содержит только эти hosts, без reverse proxy и access logging.
4. Импортов в доступном `/etc/caddy/Caddyfile` нет.
5. Caddy stdout направлен в journal; доступ к `/var/log/caddy` для проверки текущим пользователем запрещён.
6. `/var/log/journal` persistent; объём всех журналов был 1.2 GB. Это не объём Caddy.
7. В выборке за последние 7 дней 110 Caddy diagnostic request objects относились к иным hosts и включали потенциально идентифицирующие сетевые поля. Значения не включены в отчёт.
8. В проверенном коде подготовленного сайта есть только указанные storage значения; сетевых API/форм/встроенных внешних ресурсов не обнаружено.

10. Caddy ACME-журнал содержит обращение к Let’s Encrypt production/staging endpoints. Исторический журнал не является проверкой актуальности сертификата.

## 14. Технические замечания и риски

- **Общий журнал с request fields:** Caddy ошибки reverse proxy записывают полный request object, включая IP, UA, URI и заголовки. В некоторых URI были query strings. Хотя найденные объекты относились к другим host, это показывает, что journald способен сохранять потенциально чувствительные запросные сведения.
- **Retention не закреплён явно:** текущая конфигурация journald не задаёт проверенные лимиты/сроки. Доступный диапазон записей не следует трактовать как утверждённый срок удаления.
- **История конфигурации не установлена:** runtime admin API и текущий `/etc/caddy/Caddyfile` указывают на deployment-копию, но mtime Caddyfile новее времени старта процесса. Это не позволяет определить, когда и кем конфигурация была активирована.
- **Исторические записи других hosts:** в выборке journald за 7 дней было 4 323 Caddy events и 110 структурированных request objects, все отнесены к другим hosts. В выборке встречались IP, URI и headers; Referer был в 85, Cookie в 34 записях. Значения не выгружались. Текущий runtime не содержит других hosts, но прошлые журналы сохраняются в общей системе.
- **Доступ к файловым логам ограничен:** `/var/log/caddy` имеет mode `750`, владелец `caddy:caddy`; listing непривилегированному пользователю запрещён. Наличие файлов и их содержимое не установлены. Правило logrotate для Caddy не найдено в доступной проверке.
- **Общий journald:** размер всех журналов около 1.2 GB; явные retention limits не обнаружены. Это не устанавливает срок хранения, а политика Snapper/backup остаётся неизвестной.
- **Публичный privacy contact отсутствует:** существующие страницы политики указывают, что официальный контакт нужно подтвердить/добавить.
- **Сведения из политики требуют актуализации:** общие формулировки о журналах, получателях и сроках хранения должны отделять подтверждённое поведение сайта от неизвестных системных/провайдерских слоёв.

- Активный основной site block не содержит отдельного access log. Сохранённый локальный кандидат устарел относительно production: он содержит дополнительные site blocks и access-log настройки `/var/log/caddy/miryolove-access.json` (rotation 10 MiB, до семи файлов, `roll_keep_for 14d`); применять его нельзя без новой сверки и согласования.
