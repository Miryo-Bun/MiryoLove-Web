# Финальная предпубликационная проверка MiryoLove

**Дата:** 7 ноября 2026 года
**Область:** локальные source/deploy файлы, доступный Caddyfile и read-only HTTPS-проверки. Конфигурация и production этим заданием не изменялись.

## Готово

- Карточка MiryoLove AI сохранена; ссылка на модель на главной и странице проекта ведёт на `https://huggingface.co/MiryoBun/MiryoLove-7B` в RU/EN. Старый AI-host отсутствует в публичных HTML/JS/CSS/XML/TXT. Liquid Glass, другие карточки и разделы не менялись.
- Deployment-копия содержит 17 публичных файлов (10 HTML, 3 изображения, CSS, JS, sitemap, robots), без `.git`, `docs/`, скрытых файлов, симлинков, README/LICENSE, служебных отчетов и распространённых проверяемых маркеров секретов.
- Опубликованные файлы синхронизированы с source. Проверены 184 локальные ссылки/ресурса, CSS URL, JS ссылки на логотипы, sitemap, robots и отсутствие чистых внутренних ссылок на `.html`.
- В deployment нет MiryoBoard и публичной дорожной карты; старые roadmap URL перенаправляются в локальном тесте на главную.
- JavaScript syntax, XML sitemap, `git diff --check` и внутренние ссылки прошли.
- Локальная проверка Caddy подтвердила 200 для девяти clean URL, 301 для старых `.html`/URL без `/`/roadmap, 301 `www` → apex с путём и query, HTTP 404 с пользовательским телом для неизвестного адреса.
- Read-only Caddy admin API и `/etc/caddy/Caddyfile` сейчас подтверждают одинаковый root `MiryoLove Web-deploy`; runtime содержит только apex/`www`, без reverse proxy и access logging. Предыдущий отчёт о root `/Web/1` был устаревшим наблюдением; точное время/способ изменения и reload не установлены.
- Публичные HTTPS GET-проверки 7 ноября 2026 года: девять canonical URL и JS/CSS/sitemap/robots — 200, специально неизвестный URL — 404; ни в одном проверенном ответе не найден `Set-Cookie`. TLS verification result — 0. HTTP→HTTPS и `www`→apex redirect сохраняют искусственный query; redirect clean URL без `/`, старых `.html` URL и roadmap URL его теряет.
- Браузерные проверки локальной копии прошли: все 10 HTML страниц, RU/EN на каждой, 70 сочетаний «страница × ширина» от 360 до 1440 без горизонтального переполнения, мобильное меню и Escape, reduced motion; ошибок консоли и сетевых failed requests не обнаружено.
- Изолированный тест кандидата подтвердил ровно поля `ts`, `level`, `logger`, `msg`, `visitor_user_agent`; timestamp — Unix epoch, соответствующий UTC. Искусственные IP/request/URL/query/Referer/Cookie/Authorization/headers/body/response-size markers не попали в запись.
- JavaScript-уведомление и privacy/cookie тексты RU/EN обновлены, чтобы описывать browser storage и отличать пока не применённый access log от системного журнала. Политика не утверждает юридическое соответствие.
- За последние семь дней в journald найдено 110 Caddy error/reverse-proxy records с полным request object, все отнесены к другим host. В записи есть IP-поля, URI и headers; значения не выводились. В 85 были Referer, в 34 Cookie. Retention неизвестен.

## Требуется администратор

- Текущий `deploy/Caddyfile.candidate` устарел относительно production: содержит дополнительные site blocks AI/press; не применять его. Нужен новый минимальный кандидат, если владелец отдельно решит менять logging.
- Текущий пользователь не может перечислить `/var/log/caddy` (mode 750, владелец caddy); наличие/содержимое журналов и право службы на подготовленный output path не проверены. Journald и Snapper retention неизвестны.
- В `/var/log` присутствуют логи Cloudflare WARP и Snapper; их содержимое и связь с посещениями сайта не проверялись.
- Неизвестны провайдерские/network logs, сроки и получатели, фактическое юридическое лицо оператора и официальный privacy contact. User-Agent может быть персональными данными в контексте обработки; требуется юридическая оценка, включая законного представителя и квалифицированного юриста с учётом предоставленной владельцем информации о несовершеннолетии.

## Требуется отдельное решение

- Не применять конфигурацию и не выполнять `systemctl reload/restart caddy` до отдельного разрешения владельца.
- Не менять DNS, права/владельцев, журналы, базы данных, snapshots или другие сервисы.
- Утвердить момент и ответственного за переключение; при необходимости согласовать окно изменений и процедуру отката по `deployment.md`.
- Получить ответы на вопросы владельца/инфраструктурного администратора в `152-fz-review.md`, затем провести отдельную юридическую проверку. Юридическое соответствие этим техническим отчётом не устанавливается.

## Итоговая оценка

Изменение ссылки модели готово локально и не опубликовано. Production Caddy config и runtime сейчас обслуживают deployment-root, но access log не включён. Подготовленный Caddy-кандидат **не готов к применению** из-за отличающихся AI/press blocks и непроверенного production log path. В этой задаче не менялись Caddy, DNS, службы, журналы, права, владельцы, базы данных или snapshots; reload не выполнялся. Retention journald/Snapper и юридическая достаточность политики остаются неизвестными.
